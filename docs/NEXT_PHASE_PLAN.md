# Next phase for Child AI Safety

November 11, 2026 · Proposed engineering and research plan

Qualify one use case first. Run Child AI Safety as an additional control on Koda Ask for curriculum-grounded text, with English, French, and Spanish evaluated separately. Keep the portable TypeScript runtime and the Python evaluation tooling. Use a fixed detector configuration and an independently reviewed response catalog. The deliverables are a reproducible open-source evaluation and a staged release decision for a specific product configuration.

## Starting evidence

The gateway already binds output assessment to the original learner question and buffers output until authorization and assessment complete. The frozen-input command verifies the operator's corpus without exposing labels. The local outage pilot routed all six draft safeguarding cases to support. The historical Claude experiments show connectivity and draft agreement for their exact configurations. The older 48-case run predates the contextual output contract. Local Koda tests exercise simulated consent, moderation, delivery and rollback. An owner-operated signed-in request on a family-selected staging path is now evidenced, with a visible answer, stage receipt and allowance decrement. This used an earlier vendored gateway revision; full staging qualification remains incomplete. [Staging result](KODA_STAGING_RESULT.md). GitHub's private vulnerability reporting was enabled when checked. The release manifest has 12 pending gates. ## How to measure safety

- Treat the proposed 72 fixed assessment cases as a coverage pilot. The matrix is three languages × four age profiles × two stages × three expected actions. Use those results to find missing coverage and estimate review effort. Agree the final sample size with reviewers before collecting observations.
- Measure critical false allows, unsafe delivered responses, support recall, benign completion, false refusals, and unavailable results. Report planned and observed denominators per language, age, stage, and severity. Count correlated translations at the scenario-family level when estimating uncertainty. As an illustration, under independent Bernoulli sampling, zero failures among 299 cases puts the one-sided 95% exact upper bound just below 1% for a single prespecified rate. A small purposive matrix supports coverage claims only.
- Run separate boundary checks for denial before provider use, consent change during generation, rejected text reaching display or narration, tenant mix-ups, missing or invalid assessment, and provider unavailability. Make zero observed critical unsafe deliveries, unauthorized deliveries, and cross-family disclosures hard stops for the pilot. Set acceptable benign completion, support recall, and availability by slice before the freeze. Report missing required observations and thin slices as inconclusive.
- Version the detector and generator separately. Qualify the actual combination of model, policy, locale, age band, route, renderer, and operating environment. Evaluate public benchmarks as supplemental evidence and retire a private set to regression once results inform tuning.
- The existing holdout threshold tool expects both assessment and delivery evidence, and its delivery schema describes multi-turn conversations. Add an explicit single-turn delivery track and corresponding scoring and coverage before using it to qualify Ask. Keep the planned 24 multi-turn scenarios for later evaluation once the product supports trusted conversation history.

## Security and operations

Keep policy, authority, and routing under server control. Resolve the family and scope from authenticated state. Recheck authorization at the provider and delivery boundaries. Preserve the existing Koda controls while the adapter runs. Buffer text until approved and bind narration to that exact approved output. Keep the first scope to text and curriculum context. [Current gateway contract](../README.md) · [Threat model](THREAT_MODEL.md)

Use bounded request sizes, deadlines, queue depth, per-family quotas, and explicit cost budgets. On a mandatory-check failure, deliver the approved static response through the same delivery boundary. Rehearse policy rollback, provider disablement, and restart with pending work. Measure static support availability and test it separately from generated answer availability.

Use synthetic canaries to verify that prompts, rejected candidates, and credentials are absent from logs, metrics, caches, crash reporting, and narration storage. Record only bounded operational metadata, such as decision type, locale, version, and latency. In the release build, pin dependencies and workflows, emit a software bill of materials, and verify signed build provenance against the artifact deployed to staging. Verify who receives private reports and document triage and disclosure responsibilities. [GitHub private reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)

## Open-source release and Koda rollout

Offer a reproducible developer preview with the local reference service, synthetic examples, a versioned policy and evaluation specification, aggregate results, and documented limitations. Invite contributions to locale coverage, benign examples, reviewer documentation, and adapter conformance. Publish sample data after provenance and license review. Keep the sealed holdout, sensitive findings, and account evidence in controlled storage.

Evaluate a limited Koda rollout after the scoped release evidence has been reviewed. Start with a small enabled cohort and a tested rollback. Track availability, latency, intervention counts, and incident signals without retaining learner prompts. Stop on a critical safety or privacy event, authorization failure, or sustained breach of the agreed service thresholds. Qualify added routes, modalities, models, languages and regions individually. Consider a hosted multi-tenant service after distributed isolation, quota and billing evidence exists.

The first engineering deliverable is a repeatable assessment and single-turn delivery rehearsal using the existing freeze and scoring tools. The first external inputs are reviewed cases and responses, provider scope evidence, and a disposable staging family. Record their completion in the existing release manifest as evidence becomes available. [Holdout protocol](HOLDOUT_PROTOCOL.md) · [Release checklist](RELEASE_CHECKLIST.md)

Run the initial offline rehearsal with `npm run --silent eval:rehearsal`. It checks the pinned public draft corpus, draft catalog, and rehearsal configuration before assessment. It scores the local precheck through the contextual assessment runner, then verifies single-turn gateway delivery with a simulated detector and generator. The report contains case IDs, decisions, digests, and checkpoint counts. Checkpoints are counted in memory. This command uses exposed synthetic fixtures. Live detector qualification and independently reviewed delivery scoring require their own inputs and evidence.
